## ADR-001. Стратегия эволюции архитектуры (от монолита к микросервисам)

**Дата:** 2026-10-01

**Статус:** Accepted

### Контекст

AdScale готовит подключение нового крупного DSP-парнера через 3 месяца.
Нагрузка на систему увеличиться на 20% процентов (18 000 RPS).
Должны быть исключены сбои и простои сервиса ставок (время отклика до 100ms), деградация SLA,
остановки бизнеса. У системы отсуствует запас производительности.
Текущая система - гибридный монолит (С++ / Go / Python / Node.js / Javascript) с единой PostgreSQL.

Ключевые архитектурные драйверы (приоритет 1):

- **Архитектура:** нельзя реализовать микросервисную архитектуру за 3 месяца
- **Сроки:** три месяца до запуска интеграции с новым DSP-партнёром
- **Бюджет:** ограничен
- **Стоимость инфраструктурных решений:** Redis + реплика БД
- **Непрерывность:** нельзя остановить платформу
- **Подключение DSP-партнёров:** интеграция с одной крупной площадкой через Ad Server
- **Вынос БД из hot path:** Redis для кампаний, стратегий ставок, таргетинга и бюджета
- **Отказ инстанции БД:** Master-Slave PostgreSQL, ручное переключение при отказе
- **Разделение критичных и некритичных потоков:** репликация + read-replica
- **Нагрузка (Scalability):** пиковая 18 000 RPS, запаса производительности нет
- **Производительность:** P95 задержка < 100 ms
- **Доступность:** SLA без деградации
- **Надежность:** исключение блокировок БД

Приоритеты 2–3 (учитываются при реализации, но не определяют выбор):

- **Распределение нагрузки:** разделение данных доменов по схемам (Пр 2)
- **Защита входящего трафика:** лимиты на прямом канале DSP, уровень AdServer/Nginx (Пр 2)
- **Корректность платежей при сбоях:** гарантия отсутствия двойного списания (Пр 2)
- **Наблюдаемость:** метрики latency/error rate + алерты по порогам SLA (Пр 2)
- **Безопасность:** HTTPS/TLS для внешних каналов (Пр 2)
- **Изменяемость:** использование универсальных механизмов подключения (Пр 2)
- **Сопровождаемость:** контейнеризация выделенных сервисов (Пр 3)
- **Стек:** C++ / Go / Python / Node.js / Javascript, PostgreSQL + Redis (Пр 3)
- **Команда:** SRE, техписателя и аналитика в штате нет (Пр 3)
- **DevOps:** нет Kubernetes / оркестратора контейнеров (Пр 3)


### Рассмотренные альтернативы
1. Переписать всё с нуля
2. Постепенный вынос сервисов
3. Остаться монолитом, но масштабировать

#### Вариант 1. Переписать всё с нуля

Плюсы
- Чистый код и современный стек без легаси
- Архитектура сразу целевая

Минусы 
- Месяцы без новой функциональности 
- Нужно параллельно поддерживать старую систему и переносить данные 
- Сложны старт для развертывания

#### Вариант 2. Постепенный вынос сервисов

Плюсы
- Бизнес не останавливается, но развивается
- Первым выносится то, что даёт выгоду быстрее всего
- Ошибка стоит недели, а не года
- Откат возможен на каждом шаге 

Минусы
- Переходный период растянут 
- Монолит и сервисы сосуществуют, нужен контроль согласованности 
- Два способа деплоя, сложнее отладка
- Нужны новые компетенции: Kafka, service mesh, распределённая отладка

#### Вариант 3. Остаться монолитом, но масштабировать

Плюсы
- Быстро: недели
- Минимум изменений в архитектуре
- Дешевле по инфраструктуре

Минусы: 
- Временное решение, проблема вернётся
- Всё по-прежнему выпускается и падает целиком
- Нагрузка на базу растёт, OLTP и OLAP не разделяются

### Решение

Выбран **вариант 2** — постепенный переход. Целевая архитектура зафиксирована в C4-схеме TO-BE

#### Принципы

1. **Целевая схема известна заранее.** Каждый шаг приближает систему к схеме этапа TO-BE, а не создаёт промежуточную архитектуру.
2. **Сначала контракт, потом код.** Сначала фиксируются API и события, затем пишется реализация.
3. **Один сервис — одна команда.** Кто вынес сервис, тот им и владеет.
4. **Откат без боли.** На каждом шаге есть возможность вернуться к прежнему поведению.
5. **Проверяем данные.** Пока старый и новый путь работают параллельно, результаты сравниваются.
6. **Измеряем до и после.** Для каждого шага выделены метрики, которые можно показать бизнесу.

#### Дорожная карта

| Этап                          | Что делаем                                                                                             | Критерий завершения                                           |
|-------------------------------|--------------------------------------------------------------------------------------------------------|---------------------------------------------------------------|
| **0. Инфраструктура**         | Kafka, RabbitMQ, Redis с Failover, Istio, мониторинг (Prometheus, OTel, Jaeger, Grafana, Alertmanager) | Все сервисы отправляют метрики и трейсы                       |
| **1. Сервис ставок**          | Вынос Bidding Service                                                                                  | p99 аукциона укладывается в бюджет, доля тайм-аутов минимальна |
| **2. Событийная статистика**  | Вынос Statistics в отдельный сервис с ClickHouse и батчевой записью                                    | Нагрузка на рабочую базу снижена, write latency в норме       |
| **3. Финансы**                | Вынос Financial Service с идемпотентными операциями, RabbitMQ и ACID-транзакциями                      | Ноль потерянных списаний, сверка без расхождений              |
| **4. Разделение OLTP и OLAP** | Аналитика на ClickHouse, чтение с реплик                                                               | Тяжёлые запросы не идут по рабочим базам                      |
| **5. Кабинет**                | Campaign Service, BFF, кэш кабинета                                                                    | Кабинет собирается из кэша, при промахе параллельные запросы  |
| **6. Реклама целиком**        | Delivery, Auction Service, service mesh для всех сервисов                                              | Система соответствует C4-схеме TO-BE                        |


### Последствия

Положительные
- Бизнес не останавливается
- Выгода видна на каждом этапе
- Откат возможен
- Инфраструктура готова для следующих шагов

Отрицательные
- Монолит остаётся источником, пока домен не вынесен
- Каждый сервис нужно поддерживать в доступном состоянии
- Отладка через множество сервисов

Риски
- Переходный период растянут (Фиксируем целевую схему и сверяем с ней каждый шаг)
- Сложнее отлаживать (Единый стек мониторинга, сквозная трассировка)
- Нужны новые компетенции (Обучение команды)
-  Рост стоимости инфраструктуры (Kafka и Redis переиспользуются всеми сервисами)

**Критерий завершения:** система соответствует C4-схеме TO-BE, каждый сервис владеет своими данными и выпускается независимо.
