## AdScale TO-BE архитектура

### 1. Ключевые архитектурные решения

1. C++ в горячем пути (Ad Server и Auction Engine написаны на языке с предсказуемой производительностью без пауз сборщика мусора)
2. gRPC там, где ответ нужен сейчас; HTTPS/REST - везде остальном.
3. Redis Cluster вместо обращения к базе данных в горячем пути.
4. Предрасчёт ставок Ставки частично считаются заранее и в момент запроса читаются из кэша и корректируются под текущее состояние бюджета и ограничения запроса.
5. Kafka для событий - гарантия доставки (at-least-once) и развязка отправителя и получателя
6. Данные разделены по доменам. Отказ одного хранилища не затрагивает остальные.
7. ClickHouse в местах, где нужна аналитика больших данных 
8. Istio для безопасности и наблюдаемости
9. RabbitMQ для задач с гарантией выполнения и повторных попыток
10. Kubernetes для оркестрации
11. Контракт - центральная сущность денег. 
12. Два независимых канала: статистика и деньги.
13. Primary + Replica для каждого домена. Запись идёт в primary, чтение уходит на replica. CQRS.

Ключевые изменения:

- **Ad Service в монолите распался на два сервиса.** Это позволяет работать с различными типами партнеров. 
  - Bidding Service принимает запросы партнёра, подбирает кандидатов и работает с кэшем. 
  - Auction Service проводит сам аукцион: читает бизнес-правила и историю, считает победителя, сохраняет результат
- **Появился Update Cache Worker** внутри Bidding Service - он слушает события Kafka и поддерживает кэш в актуальном состоянии. Именно он позволил убрать базу данных из горячего пути.
- **Financial Service получил три воркера** с разными задачами: 
  - Contract Worker обрабатывает события контрактов и создаёт списания, 
  - Credit Worker ведёт пополнения и общается с платёжным шлюзом, 
  - Transaction Worker проводит операции по бюджету и счетам.
- **Statistics Service получил собственное хранилище на ClickHouse.** Раньше действия писались в общую базу; теперь у сервиса своя аналитическая база и отдельный Action Worker.
- **Выделено 2 кеша:** 
  - `bidCache` (Redis Cluster BC) обслуживает аукцион и держит одиннадцать наборов данных. 
  - `advertiserCache` (Redis Cluster Primary/Replica) обслуживает кабинет рекламодателя. Раньше кэша не было вовсе - каждый запрос шёл в базу данных.
- **Единая PostgreSQL разделена на независимые хранилища** по доменам: Campaign DB, Financial DB, Delivery DB на PostgreSQL и ClickHouse для статистики и аналитики.

### 3. Потоки данных (из диаграммы C4 TO-BE)

#### Сценарий 1: Работа в кабинете рекламодателя (кампании, пополнение бюджета, аналитика)

- **Просмотр кабинета**
  - Рекламодатель -> API Gateway: запрос открытия кабинета
  - API Gateway -> Advertiser Dashboard BFF через Istio Sidecar: запрос стартовой страницы
    - Advertiser Dashboard BFF -> `advertiserCache`: получить закэшированные данные рекламодателя: профиль, баланс, список кампаний, агрегаты
    - Если данные устарели или отсутствуют: параллельные запросы с тайм-аутом 2 с, двумя повторами и размыкателем (порог 50 %, пауза 30 с):
      - Advertiser Dashboard BFF -> Campaign Service через Istio Sidecar: получить кампании (`adCampings`)
      - Advertiser Dashboard BFF -> Analytics Service через Istio Sidecar: получить агрегаты (`aggregates`)
      - Advertiser Dashboard BFF -> Financial Service  через Istio Sidecar: получить бюджеты (`budgets`)
    - Advertiser Dashboard BFF -> `advertiserCache`: Запись полученных данных
    - Advertiser Dashboard BFF -> собственный расчёт: сборка стартовой страницы
    - Advertiser Dashboard BFF -> `advertiserCache`: Запись вычисленной стартовой страницы
    - `advertiserCache` Primary -> `advertiserCache` Replica: репликация
  - Ответ рекламодателю: кабинет, собранный из четырёх источников

- **Управление кампаниями, контентом и стратегиями ставок**
  - Рекламодатель -> API Gateway -> Campaign Service через Istio Sidecar: создание, изменение, удаление или чтение кампании, контента, стратегии
      - **POST / PATCH / DELETE:**
        - Campaign API -> Campaign Business Logic: обработка и валидация изменений
          - Campaign Business Logic -> Campaign DB Primary: сохранение кампаний, контента, стратегий (`campaigns`, `content`, `strategy`)
          - Campaign DB Primary -> Campaign DB Replica: репликация записанных данных
          - Campaign Business Logic -> Kafka (Producer): события `campaign_changed`, `content_changed`, `strategy_changed` (обрабатываются асинхронно, см. Сценарий 5)
      - **GET:**
        - Campaign API -> Campaign DB Replica: чтение текущего состояния (`campaigns`, `content`, `strategy`)

- **Пополнение бюджета**
  - Рекламодатель -> API Gateway -> Financial Service через Istio Sidecar: запрос пополнения
    - Дальнейшие шаги - Сценарий 4 «Финансы»

- **Просмотр финансов**
  - Рекламодатель -> API Gateway -> Financial Service через Istio Sidecar: чтение `budgets`, `state_budgets`, `transactions`, `accounts`
    - Дальнейшие шаги - Сценарий 4 «Финансы»

- **Запрос отчёта**
  - Рекламодатель -> API Gateway -> Analytics Service через Istio Sidecar: запрос отчёта
      - Analytics API -> RabbitMQ: задача на формирование отчёта (`report`)
      - Ответ: 202 Accepted
  - Reports Worker <- RabbitMQ: получает задачу (`report`)
    - Reports Worker -> ClickHouse Replica: получает события (`events`) и формирует отчет
    - Reports Worker -> ClickHouse Primary: сохраняет сформированный отчёт (`reports`)
    - Reports Worker -> Рекламодатель : уведомление о готовности
  - **Обработка ошибок:** при тайм-ауте или ошибке - возврат в очередь с нарастающей задержкой; после нескольких попыток - в очередь необработанных задач (DLQ)


- **Приём событий для аналитики**
  - Analytics Worker <- Kafka (Consumer): все бизнес-события рекламных капаний: `campaign_changed`, `content_changed`, `strategy_changed`, `action_endUser`, `targeting_changed`, `state_budget_changed`, `transaction`, `contract_create`, `contract_deactivate`, `contract_completed`
    - Analytics Worker -> ClickHouse Primary: батчевая запись событий и агрегатов (`events`, `aggregates`)
    - Analytics Worker -> Kafka (Producer): событие `analytics_changed` (запускает обновление кэша кабинета, см. Сценарий 5)

- **Просмотр аналитики**
  - ClickHouse Primary -> ClickHouse Replica: репликация `events`, `aggregates`, `reports`
  - Рекламодатель -> API Gateway -> Analytics Service через Istio Sidecar: чтение `reports`, `aggregates`
    - Analytics API -> ClickHouse Replica: получает готовые отчёты и агрегаты

#### Сценарий 2: Запрос партнёра (горячий путь)

**Бюджет времени: менее 80 мс p99 на всю операцию.**

- **Уровень Bidding Service**
  - DSP-партнёр -> API Gateway : запрос ставки (`bid request`)
    - API Gateway -> Ad API  через Istio Sidecar: проверка: ограничение частоты для партнёра, аутентификация, размыкатель
      - Ad API -> Ad Server: запуск отбора кандидатов (кампании, таргетинг пользователя, ограничения слота)
          - Ad Server -> `adCache`: получить закэшированные кампании и таргетинг пользователя и отбор кандидатов (`candidates_list`)
            - Наборы данных `adCache`: кампании; стратегии (правила бюджета, правила таргетинга, поправки); контент; баннеры; таргетинг по пользователю; агрегаты таргетинга по кампании; состояние бюджетов; бюджеты; резервы бюджетов; агрегаты бюджетов; предрассчитанные ставки
          - **Если в ответе сразу требуется баннер:**
            - Ad Server -> `adCache`: получить баннеры отобранных кампаний (`banner_list`) и отсев кандидатов по наличию баннера (`candidates_list`)
          - **Если кандидатов нет:** Ad Server -> Ad API: ответ `no-bid`
          - **Если кэш пуст:** Ad Server -> Ad API: ответ `no-bid`; 
            - Ad API -> Kafka (Producer): инициализация кэша (`bid_cache_init`, см. Сценарий 5)
          - Ad Server -> `adCache`: получить стратегии, таргетинг кампании, состояние бюджета, предрассчитанные ставки и применение поправок по ограничениям аукциона и состоянию бюджета с учётом резервов (`candidates_bids`)
          - **Если требуется собственный аукцион и Auction Service доступен** (тайм-аут 10 мс, один повтор, размыкатель 50 %/30 с):
            - Ad Server -> Istio Sidecar Auction Service через Istio Sidecar: запуск аукциона (список кандидатов, рассчитанные ставки)
                - Auction API -> ClickHouse Auction: бизнес-правила и история аукционов (`rules`)
                - Auction API -> Auction Engine: расчёт победителя (`candidate list`, `calculated_bids`, `rules` -> `winner`, `winner_bid`)
                - Auction API -> ClickHouse Auction: сохранение истории аукциона и результата (`candidates_data`, `auction_result`)
              - Ответ: `winner`, `winner_bid`
            - **Если аукцион не проводится:** Ad Server -> `adCache`: создание резерва бюджета кандидата
          - Ad Server -> `adCache`: создание резерва бюджета победителя (`reserve_budgets`, изменение `state_budgets`) и формирование списка контрактов по типу аукциона (`contract list`)
        - Ad API -> Ad Server: формирование ответа партнёру (список контрактов, список баннеров)
      - Ответ: `bid response`
  - Ad API -> Kafka (Producer): событие создания контракта (`contract_create`, см. Сценарий 3)

#### Сценарий 3: Действия с рекламой (статистика и контракты)

- **Действие пользователя или площадки**
  - Площадка/Пользователь -> API Gateway: проигрыш, выигрыш, показ, клик по баннеру
    - API Gateway -> Delivery Service через Istio Sidecar:  действие с рекламой
      - Delivery API -> Delivery DB Primary (JDBC read) - поиск дубля (`responses`) и дедупликация запросов
        - **Если дублей нет:**
          - Delivery API -> Delivery DB Primary: сохранение запроса (`responses`)
          - Delivery DB Primary -> Delivery DB Replica (streaming): репликация
          - **Проигрыш:** Delivery API -> Kafka (Producer): `contract_deactivated`
          - **Выигрыш:** Delivery API -> Kafka (Producer): `contract_activated`
          - **Показ:** Delivery API -> Delivery DB Replica: тип действия по URL (`type_url`); 
            - Delivery API -> Kafka (Producer): `action_endUser`
        - **Если нужно вернуть баннер:**
          - Delivery API -> Delivery DB Replica: получить баннер, сформированный во время запроса рекламы (`banners`)

- **Сохранение статистики и обновление таргетинга**
  - Action Worker <- Kafka (Consumer): условие контракта по действиям (`contract_action_task`)
  - Action Worker <- Kafka (Consumer): действие пользователя (`action_endUser`)
    - Action Worker -> Statistics Business Logic: обработка батча действий
      - Statistics Business Logic -> Statistics ClickHouse Primary: батчевая запись действий и производного таргетинга (`action_EndUser`, `users_targeting`, `campaigns_targeting`)
        - Записывается батчем по окну, а не на каждое действие - это снижает нагрузку на хранилище
      - Statistics ClickHouse Primary -> Statistics ClickHouse Replica: репликация
      - Statistics Business Logic -> Kafka (Producer): событие `targeting_changed` (обновляет `adCache`, см. Сценарий 5)
    - **Если условие контракта выполнено после сохранения батча:** 
      - Action Worker -> Kafka (Producer): `contract_completed`

- **Контракты и списание**
  - Contract Worker <- Kafka (Consumer): события контрактов: `contract_created`, `contract_activated`, `contract_deactivated`, `contract_completed`
    - Contract Worker -> Financial Business Logic: действие с контрактом
      - **`contract_create`:** создание контракта (`contract`) и резерва бюджета (`reserve_budget`) в Financial DB
      - **Другие события:** обновление контракта (`contract`)
        - **`contract_activate`:** 
          - Financial Business Logic -> Kafka (Producer): `contract_action_task`, перечень ожидаемых действий для выполнения контракта
        - **`contract_deactivate` и `contract_completed`:** 
          - удаление резерва бюджета (`reserve_budget`)
        - **`contract_completed`:** 
          - создание списания (`debit`); 
          - Financial Business Logic -> RabbitMQ : задача `transaction` (тип `debit`, см. Сценарий 4)
      - Financial DB Primary -> Financial DB Replica: репликация

#### Сценарий 4: Финансы (пополнение, операции, просмотр)

- **Пополнение бюджета**
  - Рекламодатель -> API Gateway -> Financial Service через Istio Sidecar: запрос пополнения
    - Financial API -> RabbitMQ: создана задача `credit`
    - Ответ рекламодателю: 202 Accepted
  - Credit Worker <- RabbitMQ: получает задачу `credit`
    - Credit Worker -> Financial Business Logic: создание пополнения
      - Financial Business Logic -> Financial DB Primary: создание записи пополнения (`credit`)
    - Credit Worker -> Платёжный шлюз: платёжная транзакция
      - **Если платёжный шлюз не ответил (тайм-аут):** Credit Worker фиксирует тайм-аут
      - **Иначе:** Платёжный шлюз -> API Gateway: обратный вызов (callback) о результате
        - API Gateway -> Financial Service: передача ответа платёжной системы
          - Financial API -> RabbitMQ: дополнена задача `credit` результатом
            - Credit Worker <- RabbitMQ: получает `credit(callback)`
    - **Если тайм-аут или ошибка в обратном вызове:**
      - Credit Worker -> Financial Business Logic: удаление пополнения
        - Financial Business Logic -> Financial DB Primary: удаление записи `credit`
      - После нескольких неудачных попыток - задача уходит в DLQ; до этого - возврат в очередь с нарастающей задержкой
    - **Если обратный вызов успешен:**
      - Credit Worker -> Financial Business Logic: обновление пополнения
        - Financial Business Logic -> Financial DB Primary: обновление `credit`
      - Credit Worker -> RabbitMQ: `transaction`

- **Идемпотентная транзакция**
  - Transaction Worker <- RabbitMQ: получает задачу `transaction`
    - Transaction Worker -> Financial Business Logic: идемпотентная транзакция
      - Financial Business Logic -> Financial DB Primary: создание операции (`transaction`)
      - Financial Business Logic -> Financial DB Primary: обновление бюджета (`budget`)
      - **Если тип операции `debit`:** обновление счёта (`account`)
      - **При успехе:**
        - Financial Business Logic -> Financial DB Primary: обновление агрегатов бюджета (`statistic_budget`)
        - Financial Business Logic -> Kafka (Producer): событие `state_budget_changed` (обновляет `adCache` и кэш кабинета, см. Сценарий 5)
      - **При ошибке:** запускается компенсирующая последовательность (сага); после нескольких попыток задача уходит в DLQ
    - Идемпотентность по идентификатору операции: повторная обработка не создаёт второе списание

- **Просмотр финансов**
  - Financial DB Primary -> Financial DB Replica: репликация
  - Рекламодатель -> API Gateway -> Financial Service через Istio Sidecar: чтение `budgets`, `state_budgets`, `transactions`, `accounts`
    - Financial API -> Financial DB Replica: чтение бюджетов, агрегатов бюджетов, резервов, операций, счетов и сборка состояния бюджета (`budgets` + `statistic_budgets` + `reserve_budgets` -> `state_budgets`)

- **Контракты**
  - Contract Worker <- Kafka (Consumer): события контрактов (`contract_created`, `contract_activated`, `contract_deactivated`, `contract_completed`)
    - Обработка описана в Сценарии 3 «Контракты»

#### Сценарий 5: Асинхронное обновление кэшей и пересчёт ставок

- **Обновление кэша ставок**
  - Update Cache Worker <- Kafka (Consumer): события `bid_cache_init`, `campaign_changed`, `content_changed`, `strategy_changed`, `state_budget_changed`, `user_targeting_changed`, `campaigns_targeting_changed`
    - **Если `bid_cache_init`, `campaign_changed`, `content_changed` или `strategy_changed`:**
      - Update Cache Worker -> Campaign Service  через Istio Sidecar: кампании, стратегии, контент рекламы
        - **Если изменился контент:**
          - Update Cache Worker -> Delivery Service  через Istio Sidecar: запрос баннера
              - Delivery API -> Delivery DB Replica: URL для ссылок в рекламе и формирование готовой рекламы
              - Delivery API -> Delivery DB Primary: создание баннера (`banners`)
              - Delivery DB Primary -> Delivery DB Replica: репликация
    - **Если `bid_cache_init`, `user_targeting_changed` или `campaigns_targeting_changed`:**
      - Update Cache Worker -> Statistics Service через Istio Sidecar: таргетинг пользователя или кампании
        - Statistics API -> Statistics DB Replica:получить таргетинг пользователя или кампании 
    - **Если `bid_cache_init` или `state_budget_changed`:**
      - Update Cache Worker -> Financial Service через Istio Sidecar: состояние бюджета (`state_budget`)
    - Update Cache Worker -> `adCache`: запись исходных данных и вычисление производных
    - Update Cache Worker -> `adCache`: запись производных: бюджетов, резервов, агрегатов бюджетов, предрассчитанных ставок

- **Обновление кэша рекламодателя**
  - Advertiser BFF <- Kafka (Consumer): события `campaign_changed`, `state_budget_changed`, `analytics_changed`
    - **`campaign_changed`:** Advertiser BFF -> Campaign Service через Istio Sidecar: получить кампании
    - **`state_budget_changed`:** Advertiser BFF -> Financial Service через Istio Sidecar: получить бюджет
    - **`analytics_changed`:** Advertiser BFF -> Analytics Service через Istio Sidecar: получить агрегаты
    - Advertiser BFF -> `advertiserCache` : записать исходные данные и сборка стартовой страницы
    - Advertiser BFF -> `advertiserCache` : записать готовую стартовую страницу
    - `advertiserCache` Primary -> `advertiserCache`: репликация

### 5. Риски

| Риск                                                    | Что делаем                                                                     |
|---------------------------------------------------------|--------------------------------------------------------------------------------|
| Расхождение данных между монолитом и сервисом           | Ежедневная сверка, сравнение по номеру версии, «теневое» сравнение решений     |
| Рост задержки из-за сетевого вызова                     | Параллельные вызовы, тайм-аут 10 мс, размыкатель, нагрузочные тесты            |
| Резерв бюджета разошёлся между кэшем и финансовой базой | Сверка раз в минуту, восстановление из финансовой базы как источника истины    |
| Платёж прошёл после тайм-аута                           | Ежедневная сверка с платёжным шлюзом, автоматическое восстановление пополнения |
| Команда не успевает                                     | Приоритет этапа, отказ от необязательной функциональности, помощь SRE          |
| Инфраструктура дороже ожидаемого                        | Поэтапный ввод, расчёт стоимости до этапа, отслеживание расходов               |
| Ключевой инженер уходит                                 | Минимум два человека на сервис, документация, записи решений                   |
