# Отказоустойчивость

## RPO и RTO по сервисам

**RPO** — сколько данных допустимо потерять при сбое. 
**RTO** — за какое время нужно восстановиться.

| Компонент                               | Хранилище                                 | RPO                                        | RTO       | Как восстанавливаемся                                                              |
|-----------------------------------------|-------------------------------------------|--------------------------------------------|-----------|------------------------------------------------------------------------------------|
| **Bidding Service (Ad API, Ad Server)** | Без своей БД, состояние в кэше            | 0 (сервис без состояния)                   | До 1 мин  | Поднимаются новые копии, состояние берётся из кэша                                 |
| **Redis bidCache**                      | Redis Cluster, Primary/Replica + Sentinel | Секунды (последние события Kafka)          | До 5 мин  | Реплика занимает роль главного, при полной потере - пересборка по `bid_cache_init` |
| **Auction Service**                     | ClickHouse Primary/Replica                | Секунды (последние записанные аукционы)    | До 10 мин | Реплика становится главной, история дописывается из потока                         |
| **Campaign Service**                    | PostgreSQL Campaign DB, Primary/Replica   | 0 (запись на главный узел)                 | До 5 мин  | Реплика становится главной, настройки не теряются                                  |
| **Financial Service**                   | PostgreSQL Financial DB, Primary/Replica  | 0 (деньги только с подтверждением)         | До 5 мин  | Реплика становится главной, незавершённые операции остаются в очереди              |
| **Delivery Service**                    | PostgreSQL Delivery DB, Primary/Replica   | Секунды (при сбое между чтением и записью) | До 5 мин  | Реплика становится главной, повторное действие распознаётся дедубликацией          |
| **Statistics Service**                  | ClickHouse Primary/Replica                | Секунды (текущий батч)                     | До 10 мин | Реплика становится главной, неполный батч перечитывается из Kafka                  |
| **Analytics Service**                   | ClickHouse Primary/Replica                | Секунды                                    | До 15 мин | Реплика становится главной, задачи отчётов остаются в RabbitMQ                     |
| **Advertiser BFF**                      | Redis bffCache                            | Не критично (кэш)                          | До 1 мин  | Копии сервиса поднимаются, кэш наполняется при первом запросе                      |
| **Kafka**                               | Кластер с копиями партиций                | 0 (при настроенных копиях)                 | До 5 мин  | Лидер партиции переизбирается автоматически                                        |
| **RabbitMQ**                            | Зеркальные очереди, DLQ                   | 0 для подтверждённых сообщений             | До 10 мин | Недоставленные задачи остаются в очереди и повторяются                             |
| **API Gateway**                         | Без состояния                             | 0                                          | До 1 мин  | Поднимаются новые копии                                                            |
| **Observability Stack**                 | Метрики, логи, трейсы                     | Допустима потеря за последние минуты       | До 30 мин | Потеря наблюдаемости не влияет на бизнес-операции                                  |

## Критичность по доменам

|        | Что                                                  | Допустимый простой  | Почему                                                     |
|--------|------------------------------------------------------|---------------------|------------------------------------------------------------|
| **P0** | Bidding Service, Auction Service, API Gateway, Kafka | Минуты              | Прямая потеря выручки, аукцион не работает                 |
| **P1** | Financial Service, Delivery Service, RabbitMQ        | До 15 мин           | Деньги и действия, нельзя потерять, но можно задержать     |
| **P2** | Campaign Service, Statistics Service, Redis bidCache | До 30 мин           | Рекламодатель подождёт, аукцион работает на имеющемся кэше |
| **P3** | Analytics, отчёты, кабинет                           | Часы                | Данные не теряются, задачи ждут в очереди                  |

## Стратегия резервного копирования

| Что                            | Частота                                             | Срок хранения  | Куда                             | Проверка восстановления                                   |
|--------------------------------|-----------------------------------------------------|----------------|----------------------------------|-----------------------------------------------------------|
| **Campaign DB**                | Полный — раз в сутки, изменения — каждые 15 мин     | 30 дней        | Отдельное хранилище, другая зона | Раз в неделю                                              |
| **Financial DB**               | Полный — раз в сутки, журнал изменений — непрерывно | Не менее 5 лет | Отдельное хранилище + архив      | Раз в месяц со сверкой сумм                               |
| **Delivery DB**                | Полный — раз в сутки                                | 30 дней        | Отдельное хранилище              | Раз в месяц                                               |
| **ClickHouse (Analytics)**     | Снимки — раз в сутки                                | 1 год          | Отдельное хранилище              | Раз в квартал                                             |
| **ClickHouse (Auction)**       | Снимки — раз в сутки                                | 90 дней        | Отдельное хранилище              | Раз в квартал                                             |
| **ClickHouse (Statistics)**    | Снимки — раз в час                                  | 90 дней        | Отдельное хранилище              | Раз в месяц                                               |
| **Redis (bidCache, bffCache)** | Не копируем как данные                              | -              | -                                | Восстановление через пересборку из источников по событиям |
| **Kafka**                      | Не копируем: копии внутри кластера                  | -              | -                                | Проверка копий раз в сутки                                |
| **RabbitMQ**                   | Не копируем: задачи живут до обработки              | -              | -                                | DLQ проверяется дежурным                                  |
| **Конфигурация и манифесты**   | В Git, резервная копия — раз в час                  | 30 дней        | Отдельное хранилище              | Раз в неделю полное пересоздание стенда из Git            |

## Соответствие принципам 12-факторных приложений

| Фактор                                           | Как реализовано                                                                   |
|--------------------------------------------------|-----------------------------------------------------------------------------------|
| **Кодовая база**                                 | Каждый сервис - свой репозиторий, сборка из Git                                   |
| **Зависмости**                                   | Манифесты зависимостей, образы с фиксированными версиями                          |
| **Конфигурация**                                 | Секреты и адреса - через переменные окружения                                     |
| **Сторонние службы**                             | Адреса PostgreSQL, ClickHouse, Redis, Kafka, RabbitMQ - через окружение           |
| **Сборка и запуск**                              | Сборка образа -> манифест -> запуск в кластере                                    |
| **Процессы**                                     | Ad API, Ad Server, Auction API, BFF, Gateway, воркеры                             |
| **Привязка портов**                              | Каждый сервис слушает свой порт; наружу - только через Gateway                    |
| **Парраллелизм**                                 | Копии сервисов и воркеров добавляются по нагрузке                                 |
| **Администрирование**                            | Сервисы поднимаются за секунды, по сигналу завершения заканчивают текущие запросы |
| **Среды разработки, тестировния и эксплуатации** | Одинаковые образы в разработке и продакшене                                       |
| **Ведение логов**                                | Логи пишутся в стандартный поток и собираются в Elasticsearch                     |
| **Расположение данных**                          | Миграции, пересборка кэша, сверки запускаются как отдельные задания               |
