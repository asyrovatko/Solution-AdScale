# 7. Репликация, шардирование, read replicas, CQRS

**Термины простыми словами**
- **Primary/Replica** — одна основная копия принимает запись, остальные копируют её. Если основная падает, её место занимает реплика.
- **Read replica** — копия, с которой только читают, чтобы разгрузить основную.
- **Шардирование** — данные делятся на части по ключу, каждая часть лежит на своём сервере.
- **CQRS** — запись и чтение идут через разные модели: пишем в одну, читаем из другой.

## 7.1. По хранилищам

| Хранилище                           | Primary / Replica                          | Шардирование                          | Read replicas                                                                   | CQRS                                                                                        | Обоснование                                                                                |
|-------------------------------------|--------------------------------------------|---------------------------------------|---------------------------------------------------------------------------------|---------------------------------------------------------------------------------------------|--------------------------------------------------------------------------------------------|
| **Campaign DB** (PostgreSQL)        | Да: Primary + Replica                      | Нет (объём умеренный)                 | Да (Чтение кампаний идёт с реплики [1.C.3a])                                    | Нет                                                                                         | Настройки читают намного чаще, чем меняют                                                  |
| **Financial DB** (PostgreSQL, ACID) | Да: Primary + Replica                      | Пока нет; при росте по `account_id`   | Да (Просмотр баланса, истории, операций [4.F.2(a)] идёт с реплики)              | Да, запись через воркеры, чтение через API                                                  | Деньги нельзя читать из рабочей таблицы под нагрузкой; реплика разгружает основную базу    |
| **Analytics ClickHouse**            | Да: Primary + Replica                      | Да (по времени и кампании)            | Да (Analytics API читает агрегаты с реплики [1.A.3a])                           | Да, это read-сторона: события пишет Analytics Worker [1.A.a.2], читают API и Reports Worker | Отчёты не должны мешать приёму событий                                                     |
| **Auction ClickHouse**              | Да: Primary + Replica                      | Да (по времени и `auction_id`)        | Да (Анализ аукционов)                                                           | Нет                                                                                         | История аукционов — большой объём, читается отдельно                                       |
| **Delivery DB** (PostgreSQL)        | Да: Primary + Replica                      | Нет                                   | Да (Поиск дубля [3.D.2], получение баннера [3.D.2.3] и типа действия [3.D.2.2]) | Нет                                                                                         | Точечные чтения по ключу; реплика снижает нагрузку                                         |
| **Stats ClickHouse**                | Да: Primary + Replica                      | Да (по времени и кампании)            | Да (Чтение таргетинга воркером [5.S.2])                                         | Да, запись - батчи действий [3.S.3], чтение: агрегаты для кэша ставок                       | Поток действий слишком велик для операционной базы                                         |
| **bidCache** (Redis 7)              | Да: Primary + Replica, Failover + Sentinel | Да (ключи распределяются по кластеру) | Да (Воркер читает кэш [1.4], реплика разгружает основную копию)                 | Да, read-модель всех данных для конкратктов, запись через воркер                            | Данные восстанавливаются из Kafka и API, поэтому достаточно реплики для отказоустойчивости |
| **bffCache** (Redis 7)              | Да: Primary + Replica                      | Да (по ключам кабинета)               | Да (BFF читает кэш [1.4], реплика разгружает основную копию)                    | Нет                                                                                         | Пользователь ждёт ответ сразу, реплика даёт запас по нагрузке                              |
| **Kafka**                           | Лидер + копии партиции                     | Да (партиции по ключу)                | -                                                                               | Транспорт CQRS                                                                              | Порядок событий сохраняется в пределах ключа                                               |
| **RabbitMQ**                        | Очереди с подтверждением, DLQ              | По очередям задач                     | -                                                                               | -                                                                                           | Каждая задача обрабатывается одним воркером                                                |

## 7.2. Что шардировать по какому ключу

| Данные               | Ключ шардирования     | Почему такой ключ                                                               |
|----------------------|-----------------------|---------------------------------------------------------------------------------|
| Финансовые операции  | `account_id`          | Все операции одного рекламодателя попадают на один шард - удобно считать баланс |
| События и действия   | `campaign_id` + время | Отчёты чаще всего строятся по кампании за период                                |
| Результаты аукционов | `auction_id` / время  | Разбор конкретного аукциона и обучение моделей по периодам                      |
| Кэш ставок           | `campaign_id`         | Кампания и её ставки должны лежать рядом, чтобы резерв бюджета был атомарным    |
| Кэш кабинета         | `account_id`          | Все данные одного кабинета лежат вместе - страница собирается за одно обращение |
